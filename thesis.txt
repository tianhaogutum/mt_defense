Abstract
Large language model (LLM) inference engines are repository-scale systems that
coordinate model management, request serving, resource-aware scheduling, native
execution, hardware adaptation, and build and deployment logic. An issue describes
where a failure is observed, not necessarily where the responsible implementation
resides, so a symptom may be repaired in a different type of artifact than the one
in which it appears. Existing research characterizes the symptoms, root causes, and
repair patterns of inference-engine bugs, or diagnoses reproducible failures at runtime,
but does not rank the concrete files that developers modify in the corresponding
pre-fix repository. To the best of our knowledge, no prior work has formulated and
systematically evaluated this issue-guided, execution-free, file-level fault-localization
task for bugs in LLM inference-engine software, so it remains unknown how effectively
existing localization approaches can address this problem.
   This thesis addresses that gap using Ollama, a widely adopted LLM inference engine,
as a case study, and a dataset of 145 validated issue–fix pairs with unambiguous, patch-
derived single-file repair labels. We evaluate two representative information-retrieval-
based (IR-based) localizers (BugLocator, BLUiR) and an LLM-agent-based approach
(SWE-agent) under two backbone models in a common execution-free setting, in which
a localizer receives an issue report and its pre-fix repository snapshot but does not
compile the repository, run tests or models, or collect new runtime traces. We find that
the IR-based approaches give imprecise but useful candidate reduction, ranking fewer
than one quarter of repair files first while about half fall within the Top-5, whereas both
SWE-agent configurations produce substantially more top-heavy rankings, reaching up
to 64.83% Top-1 (94 of 145 cases) and 88.97% Top-5 (129 of 145 cases). The two approach
families expose a clear trade-off between ranking effectiveness and computational cost,
and manual coding of LLM-agent failure trajectories attributes localization misses to
three recurring, identifiable pitfalls: evidence non-reachability, causal-chain truncation,
and non-source-artifact under-inspection, rather than to unexplainable model behavior.
   Motivated by these bottlenecks, we then present ClueFL (Cross-Software-Layer Under-
standing of Evidence for Fault Localization), a domain-specific fault-localization framework
that combines project-specific software-layer knowledge, historical issue–fix retrieval,
and a root-cause taxonomy during hypothesis generation, together with purpose-built
tools for tracing cross-layer dependencies, retrieving code metadata, and inspecting indi-

1. Introduction
Large language models (LLMs) are increasingly deployed in interactive applications,
developer tools, and local artificial intelligence services. Their practical use depends
on systems software that executes pretrained models and mediates among model
representations, heterogeneous hardware, and downstream applications. Following
prior work, this thesis refers to this repository-scale software as an LLM inference en-
gine: beyond model execution, it includes the request-serving, model-management,
resource-allocation, backend-selection, configuration, build, and deployment compo-
nents required to deliver inference functionality [Liu+26b]. Faults in this infrastructure
can affect the availability, correctness, and security of many downstream applications
[Liu+26b; Zha+26c].
   An LLM inference engine is not a self-contained model-execution module. It coor-
dinates request processing, model loading, scheduling, resource management, native
execution, hardware adaptation, and build and deployment support while accommo-
dating changing model architectures, operating systems, accelerators, drivers, model
formats, and configurations [Liu+26b; LW26]. These responsibilities are tightly cou-
pled: a symptom observed through an application programming interface (API) or a
command-line interface (CLI) may originate in a different functional region and be
repaired in a different type of repository artifact.
   Existing research addresses adjacent but distinct diagnostic tasks. Empirical stud-
ies characterize the symptoms, root causes, and repair patterns of inference-engine
bugs [Liu+26b]; static issue-centric approaches predict coarse root-cause or module
categories [LW26]; and runtime approaches diagnose reproducible failures at the state
or component level using intermediate states, traces, metrics, or fault injection [Gu+26;
Sch+26]. Although these studies provide valuable diagnostic knowledge, they do not
rank the concrete files that developers modify in the corresponding pre-fix repository.
This leaves a distinct fault-localization problem unaddressed. Given an issue report
and its corresponding pre-fix repository snapshot, a localizer must identify the concrete
file that developers subsequently modify to repair the reported bug.
   To the best of our knowledge, no prior work has formulated and systematically
evaluated this issue-guided, execution-free file-level fault-localization task for bugs
in LLM inference-engine software. Accordingly, it remains unknown how effectively
existing localization approaches can address this problem.

   Fault-localization approaches rely on different evidence sources [Won+16]. Execution-
based approaches derive suspiciousness from passing and failing executions but cannot
be applied consistently here: historical revisions may require models, hardware, con-
figurations, or runtime states that are unavailable, while silent or nondeterministic
failures may lack a reliable oracle. Information-retrieval-based fault localization (IRFL)
remains applicable because it ranks repository files based on their correspondence to
a bug report [ZZL12; Sah+13]. Directly prompted LLMs can reason beyond surface
vocabulary, but preselected code may exclude the repair file and full-repository prompt-
ing is impractical under context and cost constraints; direct reasoning therefore does
not solve candidate discovery [Wu+23]. In recent studies, it has been found that LLM
agents can instead search a repository iteratively, though generic access to tools does
not ensure that they follow the causal path from symptom to repair location [KAY24;
Zho+26]. These considerations motivate evaluating IR-based and LLM-agent-based
approaches in a common execution-free setting.
   This thesis studies an explicitly execution-free setting. A localizer receives a cleaned
issue report and its pre-fix repository snapshot, but does not compile the repository,
run tests or models, or collect new runtime traces. Existing logs and stack traces
in the report remain admissible. The setting targets bugs for which reproducible
execution evidence is unavailable or prohibitively expensive; it does not imply that
execution-based localization is generally unsuitable.
   Moreover, the fault localization in LLM inference engines is especially challenging
for three reasons:

   • Repository scale and artifact heterogeneity. At the Ollama snapshot closest to
     the dataset-collection cutoff, the repository contained 1,254 tracked files and ap-
     proximately 324,000 lines of implementation, build, and template code, including
     about 238,000 lines of Go, 69,000 lines of C/C++ and header code, and 10,000 lines
     of TypeScript.1 Relevant logic is distributed not only across these languages but
     also across source and non-source artifacts, including configuration files, build
     specifications, workflows, templates, and model metadata [Oll26a]. This produces
     a large and heterogeneous candidate space that cannot be inspected exhaustively.

   • Architectural coupling and symptom–repair distance. An issue describes where
     a failure is observed, not necessarily where the responsible implementation
     resides. Prior work identifies 28 root causes spanning input/output handling,
     configuration, functionality, environment, and resource management, and shows

   • RQ1 – Feasibility Exploration: Despite the aforementioned challenges, are repre-

acquisition and management, API serving and request orchestration, resource-aware
scheduling, inference runners, hardware-specific backends, and platform-specific build
and deployment artifacts [Oll26a]. These elements correspond to the common inference-
engine workflow of engine setup, model conversion, and inference/serving, as well

2. Background
This chapter defines the task, the admissible evidence, and the inference-engine concepts
needed by the remainder of the thesis. It deliberately does not survey competing
localization approaches. That comparison is deferred to Chapter 3, where differences
in evidence requirements, output granularity, and target scope can be made explicit.


2.1. Task Definition and Terminology
2.1.1. Failure, Fault, and Repair-Location Labels
A failure is an externally observed deviation from expected behaviour, whereas a fault is
a program element or state capable of causing that failure. Fault localization (FL) aims
to identify program elements associated with a fault and commonly returns a ranked
list of suspicious files, methods, or statements [Won+16]. The task studied in this thesis
is:

      "Given a cleaned issue report and the corresponding pre-fix repository
      snapshot, rank the eligible repository files so that the developer-modified
      repair file appears near the top of the ranking."

   The exact causal fault is rarely observable in a repository-mining study. Instead, files
modified by the accepted developer fix provide observable repair-location labels. Such
labels do not prove that every changed file independently contained a root cause, or
that no alternative repair would have been valid. This thesis therefore uses repair file
when interpreting a label and retains ground truth only in formal metric definitions. To
avoid ambiguity in set-valued labels, effectiveness analyses use single-target instances
whose accepted fix modifies exactly one eligible repair file. The dataset-construction
chapter defines the corresponding inclusion rules.
   The output is a repository-level, file-granularity ranked list. Here, repository-level de-
scribes the search scope rather than requiring the output to enumerate every repository
file: a method may omit candidates assigned a score of zero. The candidate universe is
intentionally not restricted to conventional source code: an eligible build specification,
workflow, configuration, template, or model metadata file may be returned when that

define file eligibility, snapshot construction, and ranking metrics.

2.1.2. Boundaries with Issue Localization, Repair, and Patch Assessment
Repository issue localization is sometimes used as a broader term for finding the code
entities relevant to a bug report, feature request, performance issue, or security issue.
In contrast, this thesis selects reports classified as bugs and evaluates their observed
repair locations. Automated program repair (APR) must additionally synthesize a
change, while repository-level issue resolution commonly judges a generated patch with
executable tests. SWE-bench, for example, pairs an issue with a repository but evaluates
a test-validated patch rather than an independent localization ranking [Jim+24]. Repair
success therefore combines at least two capabilities: finding a useful location and
constructing an acceptable change.
   Automated patch-correctness assessment (APCA) starts even later in the pipeline: it
estimates whether an already generated patch is semantically correct. Learned assessors
such as APPT and RePaCA are relevant to the reliability of repair pipelines, but they
neither retrieve a repair file from a repository nor measure an execution-free file
ranking [Zha+24; Fus+26]. These task boundaries prevent repair or patch-classification
accuracy from being reported as localization accuracy.


2.2. Evidence Regime
In this thesis, execution-free means that the localizer does not compile the target revision,
run the engine or its tests, instrument the program, inject faults, or collect new runtime
traces. The localizer receives only the cleaned issue report and the pre-fix repository
snapshot. The issue may contain logs, measurements, reproduction steps, or an
exception trace supplied by the reporter. These are historical artifacts already present
at reporting time; they are not dynamic signals generated by the localization approach.
   This definition is stricter than coverage-free and more precise than test-free. A coverage-
free approach may still require a failed-test output, crash dump, execution trace,
or reference run. Conversely, an execution-free approach may read a stack trace
embedded in the issue without executing the old revision. The distinction matters
because approaches described as “bug-report based” can have materially different
evidence requirements. It also rules out quietly supplementing a sparse historical
report with signals that were not available in the controlled experimental setting.
   The case-specific evidence consists of a cleaned issue report and the correspond-
ing pre-fix repository snapshot. Each approach receives the same version of these
inputs, making the ranking task comparable across classical retrieval and LLM-based

approaches. Method-specific static knowledge and retrieval resources are documented
separately.


2.3. LLM Inference Engines
2.3.1. Role and Serving Workflow
An LLM inference engine is systems software that executes pretrained models and
mediates among model representations, heterogeneous hardware, and downstream
applications. Besides model execution, it includes request serving, model management,
resource allocation, backend selection, configuration, build, and deployment compo-
nents [Liu+26b]. During serving, prefill processes the prompt and constructs attention
state; repeated decode iterations then generate tokens. Their different computation and
latency profiles create scheduling and memory-management trade-offs [Agr+24].
   Representative engines emphasize different parts of this workflow. Orca introduced
iteration-level scheduling and selective batching [Yu+22]. vLLM introduced PagedAt-
tention and block-based management of the key–value cache [Kwo+23]. Sarathi-Serve
combines chunked prefill with stall-free scheduling [Agr+24], while SGLang combines a
language-level frontend with an optimized runtime and cache reuse [Zhe+24]. Ollama,
the empirical subject of this thesis, combines local model management, command-line
and Hypertext Transfer Protocol (HTTP) interfaces, model metadata and templates, Go
and native inference paths, hardware discovery, and deployment tooling [Oll26a]. It is
not assumed to be architecturally equivalent to a distributed datacentre engine such as
vLLM or SGLang.

2.3.2. Repository Heterogeneity
Inference behaviour emerges from interactions among public interfaces, request orches-
tration, model representation, scheduling and cache policy, native kernels, hardware
backends, and build or deployment artifacts. A repository-level localizer must conse-
quently search across languages and artifact types. In Ollama, source files coexist with
model templates, build rules, dependency manifests, workflows, and configuration.
Restricting the candidate universe to a single language or extension would encode a
location answer before localization begins.
   The unit called a software layer later in this thesis is an operational grouping of
repository responsibilities, not a neural-network layer. The repository-specific layer
inventory and diagnostic checklist are contributions of ClueFL; they are therefore
introduced and operationalized in the framework chapter rather than presented here
as established background.

2.3.3. Symptom–Repair Distance
An issue is written at the level at which a failure becomes visible, but its repair may lie
elsewhere. An API error can originate in model metadata, runner selection, a native
runtime, a hardware backend, or a build rule. The words in the report can therefore
have little overlap with the responsible file. This thesis calls the resulting separation in
vocabulary and software responsibility cross-software-layer semantic distance.
   Empirical evidence supports treating this distance as a domain characteristic. The
study by Liu et al. analyses 929 bugs across five inference engines and reports root
causes spanning input/output processing, configuration, functionality, environment,
and resource management [Liu+26b]. Li and Wang likewise describe tightly coupled
software and hardware modules in vLLM and TensorRT-LLM [LW26]. These published
classifications motivate attention to cross-component failures, but they are not copied
into the present chapter as a localization procedure.

2.3.4. Limited and Uneven Diagnostic Evidence
Historical issues do not consistently provide a failing test, complete reproduction envi-
ronment, log, or stack trace. Reproduction may require a specific model, accelerator,
driver, operating system, memory capacity, configuration, or transient runtime state.
Silent and nondeterministic failures may offer no reliable pass/fail oracle [Liu+26b;
Gu+26]. Consequently, the amount and specificity of admissible evidence vary substan-
tially across reports. Execution-free localization does not solve this scarcity; it studies
what can be inferred under it.


2.4. Summary
The thesis evaluates a temporally controlled, execution-free ranking of repair files in
a heterogeneous inference-engine repository. Its labels are observed developer repair
locations rather than uniquely proved causes. The domain is challenging because a
visible symptom may be semantically and architecturally distant from a repair in source
or non-source artifacts. The next chapter asks which parts of this setting are already
addressed by prior localization, repository-agent, benchmark, and inference-engine-
reliability research.

3. Related Work and Thesis Positioning
This review covers publications available by 17 August 2026. Peer-reviewed versions
are cited where available; recent preprints are treated as provisional evidence. Methods

3.1. Execution-Dependent Fault Localization
Spectrum-based fault localization instruments passing and failing executions and de-
rives suspiciousness from their coverage. Mutation-based fault localization observes
how injected variants change test outcomes; Metallaxis-FL is a representative tech-
nique [PT15]. Such approaches can produce fine-grained rankings when a reproducible
failure, an adequate test suite, and a meaningful oracle are available [Won+16].
   LLM agents can organize the same dynamic evidence. AutoFL uses tool calls to
inspect test-covered classes and methods [KAY24]. AgentFL stages fault comprehen-
sion, navigation, and confirmation [Qin+24]; its peer-reviewed successor SoapFL uses
failing-test behaviour and coverage in a method-level procedure [Qin+25b]. FlexFL
accepts reports, tests, or both, obtains a small method candidate set, and applies LLM
refinement [Xu+25]. MemFL combines a static project summary with a dynamic mem-
ory formed from prior test-based localization attempts [YRB25]. SieveFL applies dense
file retrieval, JaCoCo execution filtering, isolated method screening, and comparative
reranking with an open model served through Ollama [FG26]. Its local deployment
is relevant to this thesis, but its central pruning signal is newly collected runtime
coverage. These works establish the value of structured reasoning, but their primary
configurations do not match a report-only file-ranking task.
   Other approaches turn a specific runtime artifact into a semantic bridge. FaR-Loc
uses a failed test and stack trace to generate a functionality description, retrieves
among covered methods, and reranks them with an LLM [SLC25]. T2L-Agent narrows
vulnerability localization from repository regions to lines using crash points, stack
traces, and abstract-syntax-tree (AST) chunks [Xi+26]. AutoCrashFL starts from a crash
dump and source repository, and is evaluated on industrial SAP HANA crashes rather

                            3. Related Work and Thesis Positioning


than issue-only bugs [Kan+25]. IssueExec retrieves tests as executable proxies for
requirements and executes them to build trace graphs [Liu+26a]. Its study reports that
existing tests reach most repair files in its Python sample, but its own threats explicitly
exclude non-runnable or test-inaccessible issues. These are strong dynamic localizers,
not matched execution-free baselines.
  SemLoc takes a different route to verifiable evidence: it converts LLM-inferred
semantic properties into typed executable constraints, evaluates their violations across
passing and failing tests, and applies counterfactual verification [Yan+26]. Its repository-
scale study is a two-stage feasibility analysis in which AutoFL first supplies a target
function and SemLoc refines it to lines. The approach therefore supports the value
of structured, checkable semantic evidence, but it does not solve the report-only
repository-file search studied here.
  Project history can also modify an existing suspiciousness signal. PAFL mines
recurring statement patterns from earlier buggy project versions and uses them to
post-process several baseline localizers [Kim+25]. It establishes project-specific fault
patterns as prior art, while differing from this thesis in granularity, baseline evidence,
and the availability of labelled historical faults.
  Recent domain-specific systems reinforce the boundary. CoHiKer localizes Linux
kernel faults with generated passing/failing tests, crash evidence, system-call context,
and dependency information [Wan+26]. EffiHolmes localizes repository-level time
inefficiencies from differential profiling and critical execution paths [YPD26]. Ekka
compares intermediate states of an optimized inference engine with a reference imple-
mentation to diagnose silent output errors [Gu+26]. Their runtime evidence is powerful
when obtainable; it cannot be reconstructed fairly for every historical Ollama issue in
the dataset used here.


3.2. Issue-Guided Retrieval and Learned Ranking
Classical information-retrieval-based bug localization (IRBL) treats the report as a
query and source files as documents. BugLocator combines textual similarity with
previously fixed similar bugs [ZZL12], while BLUiR indexes structured report and code
fields [Sah+13]. Bench4BL showed that revision matching and dataset construction
materially affect reported performance [Lee+18]; FinerBench4BL transforms the file-
level benchmark into a method-level evaluation framework and reports the resulting
accuracy–inspection-effort trade-off [THA23]. The family is inexpensive and transpar-
ent, but lexical retrieval is vulnerable to symptom–repair vocabulary mismatch and is
often limited to source files [Niu+25].
   IncBL addresses operational scalability rather than a new relevance model: it updates

                           3. Related Work and Thesis Positioning


BugLocator-style retrieval incrementally as reports and repositories evolve, reducing
recomputation while preserving the original ranking accuracy [Yan+21]. Faster model
maintenance is therefore not evidence of better semantic localization.
   LLMs can intervene without removing the explicit retrieval stage. BRaIn uses LLM-
generated relevance feedback for reformulation and reranking [SR25]; LLM-BL expands
the report, compresses retrieved code, and performs zero-shot listwise reranking [Li+25].
GenLoc combines semantic retrieval with iterative code exploration and evaluates file
localization on Java issue data, GHRB, and SWE-bench Lite [AYM26]. SweRank
learns issue-conditioned retrieval and reranking from issue–change pairs [Red+26].
HyperFL further adapts the issue representation itself by generating query-specific
low-rank adaptation parameters while keeping code embeddings reusable [Sha+26b].
Its evaluation reinforces that issue reports vary substantially in structure and diagnostic
content, although its learned corpus and target universe remain source-code files and
functions. These systems make candidate generation visible, which is valuable for
diagnosing a miss.
   More specialized hybrids clarify what the LLM contributes. LLmiRQ selects query
strategies from report content and adds conversational reformulation and learning-to-
rank features [SY24]. CosFL asks an LLM to describe the functionality of potentially
faulty methods, then performs multi-granular semantic code search [Qin+25a]. LLMLoc
combines semantic retrieval with structural embeddings for zero-shot function local-
ization [NY25]. LLMAO instead adapts pretrained representations for coverage-free
line ranking inside an already bounded source file [Yan+24a]. The first three improve
retrieval or ranking over a defined code corpus; LLMAO begins after repository-level
file selection. None demonstrates discovery of eligible configuration, build, workflow,
or metadata targets.
   The 2026 literature shifts attention from the ranking model alone to the repre-
sentation retrieved. A controlled study of five repository representations finds that
role-aware summaries can retain strong localization utility at a fraction of raw-code
context [CCC26]. Reformulate–Retrieve–Localize uses an LLM-refined query before
Best Matching 25 (BM25) retrieval and then an agentic selection stage [CM26]. BLAgent
uses AST- and path-aware encoding, dual query transformation, compact retrieval,
and bounded agentic reranking [MU26]. Its strong SWE-bench Lite results show that
structured retrieval plus reranking is already an established design; it does not, how-
ever, evaluate inference-engine-specific artifact relations or the same source/non-source
candidate universe as this thesis.

3.3. Repository-Scale LLM Exploration
General issue-resolution agents search a repository while attempting a patch. SWE-
agent introduced an agent–computer interface for repository interaction [Yan+24b];
OpenHands provides a broader platform for software development agents [Wan+24];
and Agentless separates repository structure, file retrieval, location selection, patch
generation, and validation [Xia+24]. These systems demonstrate repository-scale
search, but end-to-end repair scores do not isolate localization quality. This thesis
therefore evaluates a localization-only adaptation of a lightweight SWE-agent interface
under a matched evidence protocol [SWE26].
   FL-specific agents add stronger repository representations. LocAgent builds a het-
erogeneous graph of directory, file, class, and function entities and gives an LLM
graph-navigation tools [Che+25]. CoSIL dynamically builds and prunes module and
function-call relations [Jia+25]. OrcaLoca combines action decomposition, priority
scheduling, and distance-aware context pruning [Yu+25]. RepoNavigator shows that
a learned agent can navigate with a highly constrained jump-to-definition action
[Zha+26b]. These approaches reduce indiscriminate context loading, although symbol-
centric navigation can make a configuration or build artifact unreachable when it is not
represented as a code entity.
   ARISE extends this graph line of work to statement nodes and intra-procedural
definition–use edges, exposing data-flow slices as on-demand agent tools [Sed+26].
On SWE-bench Lite it improves function- and line-level localization over its host agent,
while increasing rather than reducing total token use and remaining limited to Python
source entities. It is direct prior art for queryable program-analysis primitives, but not
for heterogeneous execution-free file ranking.
   BugCerberus uses separate models and representations to narrow localization from
files to functions and statements [Cha+25]. SeeRepo takes a different representational
route: it renders repository structure as a visual graph while retaining source text for
precise inspection [Ma+26]. Its SWE-bench Verified experiments suggest that visual
structure is most useful during localization rather than repair or validation, but the
evidence is Python-only and its end task remains issue resolution.
   GraphLocator explicitly models the path from reported symptom to potential cause as
a dynamically constructed issue graph [Liu+26c]. RGFL adds per-file natural-language
reasoning and embedding/LLM ranking after Agentless-style retrieval [Sep+26].
HiLoRM instead trains a hierarchical reward model to select among sampled file-,
function-, and line-level predictions [Zha+25]. Together, these works mean that graph
navigation, causal framing, hierarchical localization, and bounded evidence inspection
are not novelty claims available to this thesis.
   Granularity studies further warn against treating a narrower location as automatically

better context. A factorial study on SWE-bench Verified reports that file-level context
dominates downstream repair performance, while broad line-level expansion can
introduce harmful noise [SPH26]. Because that study supplies ground-truth locations to
isolate patch generation, it is an optimistic context-selection result rather than evidence
that a practical file localizer found those files.
   Two adjacent benchmarks broaden the notion of evidence and artifact. LIDL builds a
knowledge graph over source code, prompts, and configurations for applications that
integrate LLMs and combines report, inferred, and available runtime evidence [Tan+26].
MM-IssueLoc contributes 652 issue–pull request pairs with controlled visual evidence
and evaluates file and function localization across 23 languages [Zha+26a]. LIDL

issue evidence; neither is an execution-free study of bugs inside an inference engine.
The latter is also outside this thesis’s text-only cleaning protocol, but it identifies a clear

3.4. Localization in Complex Systems Repositories
LinuxFLBench and LinuxFL+ are the closest system-software benchmarks [Zho+26].
They curate 250 Linux-kernel tasks and evaluate file- and method-level localization;
LinuxFL+ adds directory awareness and expands issue evidence with potential causes
and mailing-list information. Their analyses expose incomplete exploration and confu-
sion among related files, which are directly relevant failure modes. The comparison
is nevertheless not matched: Linux kernel tasks are C-oriented and their history en-
richment does not correspond to the temporally restricted, issue-only evidence used
here. CoHiKer is still more evidence-rich because it generates contrasting test execu-
tions [Wan+26].
   ConFL is a closer execution-free domain-aware neighbour: from a bug report it
constructs a Java concurrency knowledge base, narrows the search hierarchically,
and ranks suspicious methods using an interaction-level domain-specific language
[Sha+26a]. Its ISSTA 2026 evaluation shows that structured domain knowledge and
report-only hierarchical reasoning are already established in a specialized FL setting.
The remaining distinction is consequently not the use of domain guidance itself, but
the inference-engine operational model, the source/non-source file universe, and the
matched historical protocol.
   These systems studies and the dynamic approaches in Section 3.1 jointly show
why “domain-aware” is not itself a novelty claim. The differentiating question is
whether domain guidance remains useful when no test execution, trace, crash dump,
or coverage-derived candidate set may be generated.

3.5. Inference-Engine Reliability and Diagnosis
Liu et al. provide the most comprehensive empirical foundation for this domain. Their
study manually analyses 929 bugs from Llama.cpp, vLLM, DeepSpeed, MLC-LLM,
and TensorRT-LLM, deriving symptom, root-cause, component, and repair classifi-
cations [Liu+26b]. The work explains why inference-engine faults cross serving and
deployment responsibilities, but it does not evaluate an approach that ranks files for an
unseen issue. Ollama is also not one of the five mined engines.
   Li and Wang study static issue-centric reliability analysis for vLLM and TensorRT-
LLM [LW26]. Their pipeline classifies issue-level causes, maps reports to predefined
modules through textual similarity, and asks an LLM for repair suggestions. This is
useful triage, but its predicted location is a coarse module rather than a repository-file
ranking, and the suggestion is not grounded in inspection of the corresponding pre-fix
implementation. Runtime studies such as Ekka or telemetry-based root-cause analysis
answer a complementary question with traces, reference executions, metrics, or fault
injection [Gu+26; Sch+26].
   Thus, prior inference-engine work supplies empirically grounded domain concepts
and diagnostic categories. It does not establish comparative file-ranking performance
for classical retrieval, a generic repository agent, and a domain-guided agent on the
same execution-free historical issues.


3.6. Datasets and Evaluation Constructs
The benchmark choice determines what a reported score means. Defects4J supports
controlled execution; Bench4BL and FinerBench4BL support report-to-file retrieval;
SWE-bench evaluates test-validated repair; LocBench and MM-IssueLoc broaden repos-
itory and evidence settings; LinuxFLBench tests complex systems software. None is
interchangeable with an Ollama-specific, temporally controlled, execution-free candi-
date ranking. The dataset created here is a domain-specific instrument rather than a
replacement for these resources.

4.1.1. Candidate Issue–PR Mining and Fix Confirmation
Figure 4.1 summarizes the eight-stage construction procedure. Stages 1–2 mine candi-
date issue–PR associations—from closed, bug-labelled issue timelines and from explicit

standalone PRs are discarded because retained instances require an issue report as the
localization query. For each candidate i, we identify the last pre-integration revision ci−
and the corresponding post-integration revision ci+ (parent/merge or parent/commit);
candidates with an ambiguous integration boundary are excluded.

dently reproduced. We extract the complete file-level change Ri = ChangedFileRecords(ci− , ci+ )
without any artifact or relevance filtering, mapping each record to its pre-fix path (old
path for modifications, deletions, and unambiguous renames). New files, unresolved

and model metadata. We then conservatively drop files that are clearly unrelated to the

is uncertain. A separate, instance-level consistency check excludes candidates whose

4.1.4. Candidate Universe and Evaluation Inputs
The procedure yields the 145 retained instances (stage 8). For each, the candidate
universe Ui = { p ∈ Fread (ci− ) | EligibleArtifact( p)} satisfies Gi ⊆ Ui and is inde-

repository-relative paths in Ui . Membership in Ui defines the files eligible for scoring
and evaluation; it does not require a method’s returned ranking to enumerate every
member of Ui . Construction may inspect the PR, fixing diff, and integration metadata to
establish provenance; at evaluation time the localizer instead receives only the cleaned
issue text and the pre-fix snapshot, with the PR description, fixing diff, integration
revision, merge message, label, and post-fix contents withheld, and any history access
bounded at ci− .

BLUiR. The study uses a multilingual adaptation of BLUiR. The original approach
separates the issue summary and description and indexes Java class names, method
names, variable names, and comments [Sah+13]. Here, the issue title and body provide
the two query fields, while the Java-specific code fields are generalized to type names,
function or method names, identifiers, and comments. Language-specific front ends
extract these fields from Go, C-family, TypeScript/JavaScript, Python, shell, and Pow-
erShell files. Eligible artifacts without comparable program structure use a plain-text
fallback rather than being removed from the candidate universe.
   BLUiR scores query–code field combinations with BM25 and sums the resulting
scores for each file [RZ09]. The fixed parameters are k1 = 1.2 and b = 0.75. Parser
failures also fall back to the plain-text representation. This preserves representation
and scoring coverage across the candidate universe but provides fewer structural fields
for unsupported or non-code artifacts. In both IR implementations, every eligible file is
scored, and the returned ranking contains all and only files with a non-zero final score,
ordered by decreasing score. Zero-scored files remain in the candidate universe but are
omitted from the output. As a reproducibility limitation, the current bundle does not
retain per-file parser/fallback manifests for all 145 historical snapshots, so it does not
report an aggregate parser-coverage percentage.

4.3. Evaluation Metrics
Let I denote the set of evaluated instances, and let gi denote the ground-truth repair
file used by the evaluator for instance i. Let Ri = (ri,1 , . . . , ri,5 ) denote the normalized
returned ranking, possibly a strict subset of the candidate universe, truncated at five.
The set of files in the first k positions is denoted by Ri,1:k , and let gi ∼ r denote the
normalized matching relation defined in Section 4.2: equality or a slash-delimited suffix
match. Top-k accuracy is reported at k ∈ {1, 3, 5}, and reciprocal rank is truncated at
five.
   We cap the evaluation at k = 5 to operationalize a bounded, practitioner-oriented
inspection scope rather than to characterize the full tail of each ranking. In a survey of
386 practitioners, Kochhar et al. found that 73.58% selected five program elements as
their minimum success threshold, while more than 80% regarded a fault-localization
session as successful only when the faulty element appeared within the top five
positions [Koc+16]. Evaluating early ranks at k ∈ {1, 3, 5} is also consistent with
recent peer-reviewed fault-localization studies, including AutoFL, SoapFL, FlexFL, and
DEVLoRe [KAY24; Qin+25b; Xu+25; Fen+26]. Accordingly, for the Ollama evaluation
dataset, we report Top-1, Top-3, Top-5, and MRR@5 to measure whether the repair file
is placed within a small candidate set and how early it appears within that set. The
smaller incremental gain later observed from Top-3 to Top-5 for SWE-agent is treated
as supporting evidence that its successful localizations are concentrated within this
inspection scope, rather than as the reason for selecting the cutoff. Our conclusions

are therefore restricted to early-rank effectiveness within the top-five cutoff and do not
characterize performance beyond rank five.

4.5. Quantitative Analysis
4.5.1. Comparison with IR-based approaches
The evaluated IR implementations deterministically score every file in the eligible
candidate universe and return all non-zero-scored files in decreasing score order, with
little per-query interaction. They are effective when the issue report contains file
names, API identifiers, model-format terms, or error strings that also occur in a repair
file. BugLocator can additionally recover recurring bug families through historical
report similarity, whereas BLUiR can emphasize terms appearing in function or type
names rather than treating the entire file as undifferentiated text [ZZL12; Sah+13].
Quantitatively, BugLocator and BLUiR localize 34 and 31 of the 145 repair files at Top-1,
respectively. By Top-5, these counts increase to 71 for BugLocator and 76 for BLUiR,
corresponding to 48.97% and 52.41%, while their MRR@5 values remain 0.3320 and
0.3187. The two IR approaches do not follow a uniform ordering: BugLocator is equal
or better at earlier cutoffs and achieves higher MRR@5, whereas BLUiR reaches a higher
Top-5, indicating that BLUiR’s structured representation trades early-rank precision for
broader recall rather than dominating BugLocator outright.
   These mechanisms nevertheless depend on an observable lexical or semantic corre-
spondence between the issue report and the file representation. In Ollama, an issue
commonly describes an externally visible symptom, while the repair concerns schedul-
ing, model metadata, native runtime behavior, hardware adaptation, or deployment
logic, so vocabulary can diverge across software layers. Repeated generic terms such as
model, server, or graphics processing unit (GPU) may also distribute retrieval scores across




                                            29
            4. Evaluation of LLM-Agent-Based Fault Localization on Ollama Bugs


many plausible files. Structured fields do not eliminate this problem when the relevant
artifact has little program structure or when the report describes an observed effect
rather than a code identifier.
   The generic agent can respond to such uncertainty by inspecting the repository struc-
ture, reading candidate files, and revising its hypothesis, letting evidence accumulate
across multiple search operations rather than through one-shot text matching, as in re-
lated tool-assisted or multi-round LLM-based localization approaches [KAY24; Qin+25b;
Che+25]. Under the present protocol, which restricts the localizer to an issue report
and a static pre-fix repository snapshot, SWE-agent with GPT-5.2 localizes 74, 105, and
109 repair files at Top-1, Top-3, and Top-5, respectively, while the DeepSeek V4 Pro
configuration localizes 94, 116, and 129, substantially exceeding both IR approaches at
every cutoff.
   Case 107 (PR 9079) illustrates why this iterative exploration succeeds where lexical
matching does not. The issue reports that the CLI progress display flickers during pull
over a Secure Shell session, with no file name, function name, or error string tying
the symptom to a location. BugLocator and BLUiR both fail to rank the repair file,
progress/progress.go, within Top-5, since the report shares little surface vocabulary
with the file beyond generic terms such as display. Both SWE-agent configurations
instead rank progress/progress.go first: reasoning that a rendering artifact tied to
terminal output implicates the progress-bar renderer lets the agent reach the correct
file even though the report contains no direct lexical cue.

4.6. Qualitative Analysis
Aggregate rank-based metrics reveal whether an accepted repair location enters the
inspection scope, but they do not explain how an agent loses that location during
repository exploration. We therefore manually inspected the failure trajectories of
LLM-agent-based approaches.

4.6.1. Evidence Reachability Failures
The first failure occurs before the agent can compare causal explanations: the evidence
needed to formulate the correct hypothesis never becomes semantically reachable. This
problem is amplified by the scale and heterogeneity of inference-engine repositories.
Table 1 of Liu et al. [Liu+26b] shows that the five engines in their sample range
from approximately 122 thousand to 20.75 million lines of code and span C/C++,
Python, and Compute Unified Device Architecture (CUDA) code. More importantly,
Figures 1 and 2 distribute deployment logic across engine setup, model conversion, and
inference/serving, with additional components for model loading, request processing,
backend-specific operators, resource management, and hardware adaptation. Although
these measurements do not characterize Ollama directly, they illustrate why a locally
coherent search can cover only a small portion of the relevant evidence space.




                                           33
            4. Evaluation of LLM-Agent-Based Fault Localization on Ollama Bugs


  Case 126 shows a concentration effect within a single subsystem. Long GPU-discovery
logs from a GPU-less Windows machine led both agents through discover/runner.go,
the scheduler, the runner lifecycle, and CUDA backend initialization. Neither agent
opened discover/cpu_windows.go, where the accepted repair corrected the Windows
CPU-discovery path. The agents did not search randomly: each assembled a plausible
explanation from salient log evidence. The failure was that this evidence narrowed the
search so strongly that a neighboring startup path never entered context.
  This case does not establish that repository size alone causes localization failure.
Rather, it shows a coverage-allocation problem that repository scale and architectural
dispersion make more severe. A robust localizer should track which deployment
phases and neighboring subsystems remain unexplored, instead of treating additional
actions within the current subtree as evidence of broad repository coverage. The early
exploration stage is therefore critical: once salient log evidence draws the agent into one
subsystem, it should not prematurely rule out neighboring subtrees, since the initial
subsystem chosen constrains almost all subsequent evidence gathering.

4.6.2. Causal-Chain Truncation
The second failure arises after relevant evidence has been found, but before the com-
plete causal chain has been traversed. An inference request does not pass through one
homogeneous implementation layer. Liu et al. [Liu+26b] model the serving path in
Figure 2 as an engine initializer and model loader followed by a request parser, job
manager, input processor, backend-specific operators, and output processor; resource
managers, backend adapters, communicators, and device-specific runtimes cut across
this path. Their Table 4 further shows that inference/serving contains all 28 identified
root-cause types, while Table 5 maps the same visible symptom to functionality, en-
vironment, configuration, resource, and input/output causes. Thus, the component
closest to an exception or malformed response is often the failure-exposure layer, rather
than the layer that created the invalid state.
  Case 86 is the clearest example. For a streaming response that lost its final to-
ken, GPT-5.2 followed the request through server/routes.go, llm/server.go, and
api/client.go. It attributed the failure to Go-side scanning and stream ordering,
but never crossed into the native response producer and returned a miss. DeepSeek
continued into llm/ext_server/server.cpp, inspected the token and final-response
path, and ranked the accepted repair location first. GPT-5.2 reconstructed a plausible
prefix of the causal chain, but stopped at both a language and a process boundary. The
desired behavior is therefore not simply to “go deeper” within one layer; it is to cross
plausible language and process boundaries, identify where state first becomes invalid,
and compare competing layer hypotheses before terminating the search.

4.6.3. Non-Source Artifact Underinspection
The third failure concerns artifact type rather than code depth. As shown in Table 4.6,
Top-5 accuracy falls from 82.14% on code/script repair locations to 51.52% on non-
code locations for the source-oriented GPT-5.2 configuration. For DeepSeek, the
corresponding values are 92.86% and 75.76%, an observed code–non-code gap of
17.10 percentage points rather than GPT-5.2’s 30.62 points. The remaining gap reflects
two observable mechanisms: some operational artifacts are never opened, whereas
others are read but under-ranked relative to plausible implementation files. The smaller
gap under the neutral profile is consistent with better artifact coverage, but the cross-
configuration difference is not a controlled estimate of the prompt effect because the
backbone, endpoint, and stochastic run also differ. The qualitative mechanism is
deliberately broader than the binary stratum: it includes build/install scripts that the
documented extension rule assigns to the Code/executable-script group, as well as
Non-code artifacts.
   Documentation cases illustrate this failure mode directly. In Case 103, GPT-5.2
confirmed that the requested API endpoint already existed and encountered an explicit
link from the client code to docs/api.md, yet it continued inspecting implementation
and test files without opening the document; DeepSeek inspected the document and
ranked it fifth. This case shows that operational-artifact underinspection is a failure
mode rather than an unavoidable property of document repairs.

  Answer to RQ3. Yes: for the evaluated failure cases, manual trajectory coding
  attributes localization misses to three recurring, identifiable pitfalls rather than
  unexplainable model behavior: evidence non-reachability, where the repair file
  never enters the model’s effective context; causal-chain truncation, where the
  agent stops at a language, process, or component boundary before reaching the
  responsible layer; and non-source artifacts underinspection, where documentation,
  configuration, or build artifacts are never opened or are under-ranked.

Furthermore, manual trajectory analysis reveals that agent misses stem from a failure
cascade of three identifiable reasoning breakdowns: evidence non-reachability, causal-

5. ClueFL: Cross-Software-Layer
   Understanding of Evidence for Fault
   Localization
Chapter 4 showed that a generic repository agent is substantially more effective than
the two IR-based localizers, but also exposed several systematic weaknesses. This
chapter introduces ClueFL, short for Cross-Software-Layer Understanding of Evidence for
Fault Localization, as a domain-specific fault localization framework for LLM inference
engines. ClueFL combines three forms of guidance—project-specific knowledge, similar
historical fixes, and a root-cause taxonomy—with a multi-step localization process that
progressively narrows down the search space. It further provides a set of purpose-built
tools for tracing upstream and downstream files along causal chains, retrieving code
metadata to conserve context-window usage, and inspecting the source code of a
specific function.
   Beyond the bottlenecks identified in Chapter 4, the design of ClueFL is also inspired
by the observable practices of human developers during debugging. Empirical studies
show that developers search for relevant code, follow incoming and outgoing dependen-
cies, revisit previously examined locations, and progressively refine their understanding
as new evidence is gathered [Ko+06; Law+13]. Developers also frequently pose reacha-
bility questions to trace how program behavior propagates across components [LM10].
More recent field evidence characterizes professional debugging as a structured and
iterative diagnostic process in which developers continuously update their mental
model, alternate between forward and backward tracing, and consult external resources
to complement code-level evidence [LC26].
   Rather than attempting to reproduce human cognition, ClueFL operationalizes
these observable practices. Project-specific knowledge anchors an initial architectural
model; similar historical fixes serve as a proxy for prior debugging experience; the
root-cause taxonomy encourages the consideration of multiple competing hypotheses;
and the cross-layer navigation tools support targeted forward and backward evidence
tracing before the candidate files are ranked. This human-inspired organization is also
consistent with recent LLM-based fault localization systems such as AgentFL, which
structures localization into comprehension, navigation, and confirmation [Qin+24]. In




                                           37
      5. ClueFL: Cross-Software-Layer Understanding of Evidence for Fault Localization


contrast, ClueFL adapts this general principle to static, file-level localization in LLM
inference engines, where faults may propagate across source code, build logic, and
configuration artifacts.
  Section 5.1 presents the framework, Section 5.2 defines the experimental setup,
Section 5.3 reports the overall results, Section 5.4 analyzes those results, and Section 5.5
presents the case studies. The chapter summary answers RQ4.


5.1. Approach
5.1.1. Overview
ClueFL is designed for the same pre-fix, repository-inspection setting as SWE-agent.
The distinction lies in how the search process is orchestrated. Rather than treating the
repository as an undifferentiated, flat collection of files, ClueFL organizes localization
into three prompt-defined phases: hypothesis generation, evidence exploration, and relevance
ranking.
   Figure 5.1 illustrates this process. To discourage premature commitment to a sin-
gle symptom software layer, ClueFL initiates hypothesis generation using an Ollama
architecture map with eight software layers, a 28-category root-cause checklist, and
similar issue–repair cases from the history. The prompt then asks for a ranking of all
software layers with scores from 0 to 1, where 0 means not relevant to the given issue
at all. During evidence exploration, ClueFL guides the agent to extend its search beyond
source code to non-source artifacts, such as build scripts and configuration files, which
may also contain the actual repair locations. In addition to standard shell-based search,
ClueFL provides purpose-built repository-navigation tools for tracing upstream and
downstream packages and files along causal chains, retrieving package-level metadata
to conserve context-window usage, and inspecting the source code of individual func-
tions on demand. These tools enable the agent to verify candidate hypotheses across
software layers and progressively narrow the search space. Finally, during the relevance
ranking stage, the agent assigns file-level confidence scores and returns all candidates
with non-zero scores as a ranked list. The number of returned files is not fixed, thereby
avoiding the forced inclusion of irrelevant files merely to satisfy a predefined quota.
The evaluator then computes the Top-k metrics from the resulting list.

5.1.2. Hypothesis Generation
The first phase constructs a diverse, project-grounded hypothesis space before the
agent begins fine-grained repository inspection. As illustrated in Figure 5.1, ClueFL
combines three complementary sources of guidance: a project-specific architectural



                                            38
      5. ClueFL: Cross-Software-Layer Understanding of Evidence for Fault Localization




                           Figure 5.1.: Overview of ClueFL.


map that indicates where a fault may reside, similar historical issue–fix pairs that reveal
where related faults were previously repaired, and a root-cause taxonomy that broadens the
agent’s reasoning about why the failure may occur. Together, these signals are used to
assign a suspiciousness score to every software layer. Layers with non-zero scores are
retained as the starting points for the subsequent evidence-exploration phase.

Project-Specific Knowledge

Modern LLM inference engines are repository-scale systems that integrate heteroge-
neous components spanning multiple programming languages and deployment phases.
As observed in the failure analysis in Section 4.6, providing a generic agent with a
flat repository view frequently leads to evidence-reachability failures and causal-chain
truncation. Without a global architectural map, the agent struggles to traverse the
semantic distance between an externally visible symptom and its underlying repair
location. To mitigate this cross-software-layer distance, ClueFL injects a project-specific
software-layer taxonomy as an explicit prior for repository navigation.
   We construct this prior through a reusable zero-shot procedure. First, we extract
an inventory of package and interface nodes from the target repository. We then
provide this inventory to Claude Opus 4.6 and ask it, without labeled examples or
manually specified assignment rules, to group the nodes according to their functional
responsibilities and positions in repository data and control flows. For the evaluated
Ollama snapshot, the inventory contains 111 nodes. The zero-shot grouping assigns 69
nodes to eight named software layers and summarizes the remaining 42 nodes in three
cross-cutting groups. The resulting taxonomy and cross-cutting groups are reported in
Appendix A.2 rather than expanded here.



                                            39
      5. ClueFL: Cross-Software-Layer Understanding of Evidence for Fault Localization


   Although the resulting architectural map is specific to Ollama, its construction
procedure is not. When applying ClueFL to another inference engine, the same
inventory-and-grouping procedure can be run on the new repository without requiring
a manually labeled architectural dataset. The number, names, and boundaries of the
generated layers may therefore differ across projects. In this sense, ClueFL reuses
the taxonomy-construction procedure rather than assuming that the Ollama-specific
eight-layer taxonomy is universally applicable. The generated map is constructed once
before fault localization and is then injected unchanged for all evaluated issues.
   During the initial hypothesis generation phase, the agent consults this structured
map to connect the observed symptom to plausible subsystems before beginning
fine-grained repository inspection. For example, a CUDA out of memory report may
prioritize the Infrastructure or Machine Learning (ML) Engine layer, whereas an OpenAI
format error may prioritize HTTP API components. The associated execution paths
further help the agent trace a symptom across layer boundaries rather than stopping at
the component that merely exposes the failure. These macro-level coordinates focus
subsequent shell-based inspection and reduce the risk of prematurely narrowing the
search to a locally plausible but causally incomplete region.

Historical Issue Retrieval

To complement the architectural prior, ClueFL leverages resolved issue–fix pairs to
identify recurring bug patterns and fault-prone artifacts. Prior work has shown that
bug histories, similar issue reports, and associated repair files provide useful local-
ization evidence [Kim+07; ZZL12; WL14]. This design serves two purposes: to reuse
project-specific developer knowledge and diagnostic experience, and to account for our
observation that faults in LLM inference engines are concentrated in a small subset of
error-prone files, consistent with prior findings for large software systems [OWB05].
   ClueFL represents issue text using term frequency–inverse document frequency
(TF–IDF) and retrieves similar historical issues through cosine similarity. Similarity
is computed from each issue’s title and truncated body. With a threshold of 0.05, all
issues scoring above the threshold are returned, without imposing a fixed result count.
   The agent receives the similarity score, issue title, and confirmed repair-file paths.
Because the benchmark history provides neither fixing diffs nor root-cause explanations,
these paths serve only as weak localization priors: they highlight potentially relevant or
recurrently faulty artifacts but do not explain why the historical fixes worked. Historical
context is therefore treated as a search heuristic rather than definitive evidence. In
tightly coupled LLM inference engines, similar visible symptoms may arise from
different root causes [Liu+26b]. Accordingly, the agent must inspect the current
repository snapshot and assess each historical clue against current evidence. The final



                                            40
      5. ClueFL: Cross-Software-Layer Understanding of Evidence for Fault Localization


candidate-file ranking remains an LLM judgment informed jointly by historical clues
and evidence from the current repository.

Root Causes Expansion

While historical issues and architectural knowledge help the agent determine where to
search, effective localization also requires plausible hypotheses about why the failure
occurs. Our qualitative analysis in Section 4.6 showed that LLM-based agents often
exhibit premature convergence and anchoring bias. After observing a symptom, they
may fixate on the most common or immediately plausible root cause while overlooking
alternative mechanisms, resulting in truncated causal reasoning.
   To mitigate this diagnostic tunnel vision, ClueFL introduces a root-cause expansion
mechanism based on the empirical taxonomy of Liu et al. [Liu+26b]. The taxonomy
identifies 28 root-cause categories specific to LLM inference engines, covering areas such
as resource management, tensor operations, scheduling, hardware compatibility, and
environment configuration. Rather than relying solely on the implicit priors acquired
during LLM pre-training, ClueFL injects these categories into the prompt as an explicit
diagnostic checklist; the complete category list and diagnostic-pattern hints follow the
taxonomy of Liu et al. [Liu+26b].
   During hypothesis generation, the checklist captures potential mappings between failure
symptoms and root-cause categories. For example, it reminds the agent that unexpected
output may arise from distinct mechanisms involving formatting, configuration errors,
numerical computation, or backend behavior. The checklist is not intended to make
the agent mechanically enumerate all 28 categories. Instead, it provides a systematic
diagnostic space for generating and comparing candidate hypotheses. By presenting
multiple potential causal mechanisms, ClueFL guides the agent to consider several
plausible explanations before beginning fine-grained evidence exploration, reducing
premature fixation on a single frequent root cause and establishing a more diverse
hypothesis set for subsequent cross-software-layer evidence verification.

5.1.3. Evidence Exploration
The evidence-exploration phase transforms the high-level hypotheses generated in the
preceding phase into concrete, file-level evidence. Before entering this phase, the agent
assigns a suspiciousness score to every software layer based on the project-specific
knowledge, retrieved historical issues, and expanded root-cause hypotheses. This layer
score serves as a search gate rather than a final localization result: every layer with
a non-zero suspiciousness score is retained for further exploration, whereas layers
assigned a score of zero are excluded from the subsequent search. In this way, Step 5




                                           41
      5. ClueFL: Cross-Software-Layer Understanding of Evidence for Fault Localization


produces a set of suspicious software layers that defines the scope of evidence collection
without prematurely committing to a particular file.
   The agent then reads all non-source files in the repository (Step 6). This is an
exhaustive inspection rather than a symptom-dependent reminder. Such artifacts
are relatively few and generally short in LLM inference-engine repositories, making
complete inspection feasible within the available context window. The inspected
artifacts include dependency manifests, build scripts, Dockerfiles, Makefiles, CMake
files, configuration files, and other maintained non-source artifacts. This step prevents
the agent from implicitly assuming that every fault must originate in runtime source
code, and ensures that build-, dependency-, configuration-, and deployment-related
repair locations remain visible throughout localization.
   For source-code exploration, directly reading complete files can flood the context win-
dow with irrelevant implementation details and cause output truncation. Following the
specialized-tool design principle of SWE-agent, ClueFL therefore replaces unrestricted
source dumping with domain- and language-aware repository-navigation utilities tai-
lored to Ollama’s Go-dominated, Go/C/C++ architecture. The toolbox exposes three
focused commands:

   • deps <package> retrieves the recorded upstream and downstream dependencies
     of a package, allowing the agent to trace causal relationships across packages and
     software layers.

   • pkg_summary <package> returns file summaries, imports, types, and function
     signatures without including the complete source files, enabling the agent to
     identify candidate files and functions at a lower context cost.

   • func <file> <function> retrieves the implementation of a specified Go or C/C++
     function, supporting targeted inspection of the code most directly related to the
     current hypothesis.

  Using these utilities, the agent systematically explores every software layer with a
non-zero suspiciousness score (Step 7). Dependency information is used to move along
possible cross-layer causal chains, package summaries narrow the search from layers
and packages to individual files, and function-level inspection provides implementation
evidence for confirming or rejecting specific hypotheses. Generic commands such as
grep, find, and bounded sed ranges remain available for lexical search and for artifacts
not covered by the specialized tools.
  The result of evidence exploration is not another set of layer- or package-level
predictions. Instead, the agent produces a set of suspicious artifacts grounded in the
collected repository evidence, with localization ultimately expressed at the file level.



                                           42
      5. ClueFL: Cross-Software-Layer Understanding of Evidence for Fault Localization


Each retained file is associated with concrete evidence such as its role in a relevant
dependency path, the presence of a suspicious function or configuration entry, or its
consistency with the reported failure mechanism. These evidence-backed suspicious
files are subsequently passed to the relevance-ranking phase.

5.1.4. Relevance Ranking
After hypothesis generation and evidence exploration, the final phase consolidates the
collected evidence into a relevance ranking of suspicious artifacts. At this point, the
high-level software-layer hypotheses have already been refined through dependency
analysis, package inspection, function-level reading, and exhaustive examination of
non-source artifacts. The ranking phase therefore operates at the file level: it does not
rank software layers or packages, but the individual repository files that may require
modification to resolve the reported issue.
   For each candidate file, the agent assigns a relevance score in [0, 1] based on the
accumulated evidence and provides a brief justification for the score. The final output
includes every file assigned a non-zero score and orders them by decreasing relevance;
files omitted from the output are treated as having score zero. Consequently, the
ranking is not restricted to a fixed minimum or maximum number of candidates. A
strongly localized issue may produce only a small set of non-zero files, whereas a
cross-layer or ambiguous issue may retain a broader candidate set.
   This complete non-zero ranking supports a flexible downstream Top-k interface.
Depending on the required inspection scope, the developer or evaluation procedure
can select the k highest-scoring files as the predicted repair locations without rerunning
the localization process. In our evaluation, the same ranked list is read at Top-1, Top-3,
and Top-5, and is also used to compute MRR@5. Thus, k determines only how many
results are returned from the ranking; it does not alter the evidence-collection or scoring
process itself.

5.5. Qualitative Analysis
5.5.1. Impact of Project-Specific Layer Knowledge
An inference-engine repository does not present its causes and symptoms within one
homogeneous layer: build configuration, runtime scheduling, and native inference code
are separated concerns that a purely code-centric search does not distinguish. ClueFL
makes this separation explicit by supplying an architecture map of software layers and
a root-cause checklist during hypothesis generation (Section 5.1.2), so that the agent can
consider a build-system explanation as a distinct hypothesis rather than as an extens
ion of the runtime code it has already read.
   PR 9425 illustrates this mechanism directly. The reported symptom is a throughput
regression on a newer GPU architecture, and both agents build the same high-level hy-
pothesis: a backend-selection or build-configuration change altered the CUDA execution
path. The SWE-agent baseline pursues this hypothesis entirely within the runtime code,
ranking llama/llama.go, runner/llamarunner/runner.go, and server/sched.go as
the most suspicious files; the ground-truth repair location, the top-level CMakeLists.txt,
never appears among its eleven ranked candidates. ClueFL reaches a different top can-
didate: guided by the architecture map, it treats the build system as a distinct software
layer from the runtime and inspects it directly. Its evidence notes that the runner log re-
ports GGML_CUDA_GRAPHS enabled and a non-default GGML_CUDA_PEER_MAX_BATCH_SIZE,
both of which are compile-time toggles defined in CMakeLists.txt rather than in any



                                            48
      5. ClueFL: Cross-Software-Layer Understanding of Evidence for Fault Localization


runtime file; on this basis, ClueFL assigns CMakeLists.txt the highest confidence score
and ranks it first, while retaining the runtime-code hypotheses, such as buffer-type
selection in llama-model.cpp and offload estimation in llm/memory.go, as secondary
candidates rather than discarding them outright.
  This case suggests that explicitly separating the build-system layer from runtime
code, rather than searching source code alone, is what allows ClueFL to consider a
repair location that a code-centric search strategy does not reach. The mechanism is
architectural framing rather than additional search effort: both agents reasoned about
the same log evidence, but only the agent supplied with layer knowledge treated the
build system as a candidate layer in its own right.

5.5.2. Impact of Historical Issue Retrieval
Beyond architectural layer knowledge, ClueFL retrieves resolved issue–fix pairs whose
text is similar to the current report (Section 5.1.2). Because faults in a given project
tend to recur in a small set of error-prone files, a sufficiently similar historical issue can
point directly at the current repair location, even when the current symptom text alone
supports several plausible root causes.
   PR 13445 shows this mechanism in a case where the surface symptom is am-
biguous. The report describes Gemma 3 producing gibberish output, including
literal special-token text, after an upstream version bump. The SWE-agent base-
line commits to a tokenization hypothesis: it ranks model/models/gemma3/model.go,
convert/tokenizer_spm.go, and the Gemma 3 prompt templates highest, reason-
ing that end-of-turn token handling regressed. The ground-truth repair location,
model/models/gemma3/model_text.go, does not appear among its top ten candidates.
ClueFL instead retrieves a near-duplicate historical issue, titled almost identically to the
current report, whose confirmed fix touched exactly model/models/gemma3/model_text.go;
a second, related historical issue returns the same file. On this basis, ClueFL ranks
model/models/gemma3/model_text.go first, attributing the regression to Gemma 3’s
sliding-window and cached-attention logic rather than to tokenization.
   This case suggests that historical issue retrieval is most useful precisely when the
current symptom is compatible with more than one plausible subsystem: rather than
requiring the agent to disambiguate root causes from the current evidence alone, a
sufficiently similar past fix narrows the search directly to a recurrently faulty file.
The retrieved fix remained a prior rather than a verified explanation, but the file it
pointed to matched the accepted repair location that a tokenization-centric reading of
the symptom did not.

5.5.3. Impact of Root-Cause Expansion
The two mechanisms above help the agent decide where to look; the root-cause expansion
mechanism described in Section 5.1.2 instead broadens why a symptom might be
occurring, guarding against the premature anchoring on a single plausible explanation
observed in Section 4.6.
   PR 6905 illustrates this effect. The report describes the Windows graphical user
interface (GUI) build of Ollama running noticeably slower than the same version
launched from the command line. Both agents correctly infer that some Windows-
only code path distinguishes GUI-launched from CLI-launched execution, but they
commit to different explanations. The SWE-agent baseline anchors on a scheduling
hypothesis: it ranks app/tray/wintray/w32api.go highest, reasoning that the tray
icon’s runtime.LockOSThread() call and its Windows message-pump event loop could
starve other goroutines. This is a plausible mechanism, but it leads the agent to fo-
cus on tray- and lifecycle-related files; the ground-truth file, llm/llm_windows.go, is
ranked only sixth. Prompted with the root-cause checklist, ClueFL instead considers
an environment/runtime-mismatch category (RD.1/RD.2) alongside the scheduling ex-
planation, hypothesizing that the GUI process inherits a different Windows process en-
vironment than the CLI, changing how the external runner subprocess is spawned and
which CUDA libraries it loads. This hypothesis points directly at llm/llm_windows.go,
which sets the process creation flags for the spawned runner, and ClueFL ranks it first.
   This case shows the checklist’s role concretely: rather than replacing the agent’s own
reasoning, it adds an alternative causal category to the hypothesis set early enough that
the agent verifies it against the evidence before settling on a si ngle explanation.

5.5.4. Impact of Repository Navigation
The preceding case studies concern which layer or file to suspect; the repository-
navigation toolbox instead determines how precisely that suspicion can be verified once
a candidate is identified. In place of unrestricted source dumping, ClueFL exposes
deps, pkg_summary, and func so that the agent can trace cross-package dependencies,
inspect package-level signatures, and read individual function bodies without flooding
the context window (Section 5.1.3).
  PR 5121 shows these tools converging on a precise, function-level root cause. The
report describes DeepSeek-V2-Lite failing to load with a CUDA out-of-memory error
immediately followed by a GGML shape assertion. Both agents correctly identify the
general memory-estimation subsystem (llm/memory.go, llm/server.go) as suspicious,
but the SWE-agent baseline can only gesture at it generically: it ranks llm/ggml.go
far down its candidate list, reasoning only that the file provides “metadata used




                                           50
      5. ClueFL: Cross-Software-Layer Understanding of Evidence for Fault Localization


by EstimateGPULayers” that could plausibly be mishandled. ClueFL instead uses
deps llm/ and deps llama/ to confirm the dependency boundary between the sched-
uler and the runtime layer, pkg_summary to shortlist llm/memory.go, llm/server.go,
and llm/ggml.go, and then reads the implementations of EstimateGPULayers and
GraphSize directly with func. This reveals that GraphSize has no case for the deepseek2
architecture and silently returns zero, forcing EstimateGPULayers into a crude fallback
that misestimates video random-access memory and triggers the reported allocation
failure. Grounded in this function-level evidence, ClueFL ranks llm/ggml.go second
with an explicit, verifiable mechanism, rather than a generic file-level guess.
   This case illustrates the toolbox’s intended effect: it lets the agent turn a plausible
file-level suspicion into a specific, checkable claim about a single function, without
paying the context cost of reading each candidate file in full.

6.1. Threats to Validity
This section discusses the construct, internal, and external validity threats to this study.
   Construct validity. The Ollama evaluation dataset treats files modified by the
developer patch as ground-truth fault locations. Although this is a common opera-
tionalization of file-level fault localization, other valid fixes may modify a different file,
and this remains a challenge for fault localization research.
   Internal validity. The main internal threat is potential contamination of pre-training
data. The Ollama evaluation dataset is constructed from the public GitHub repository
of Ollama, and some issue reports, pull requests, and fixing changes may therefore
have appeared in the pretraining data of the evaluated language models. For example,
GPT-5.2 has a documented knowledge cutoff of 31 August 2025,1 which overlaps with
part of the cases in the Ollama evaluation dataset. For DeepSeek V4 Pro, the complete
training corpus and an equally precise knowledge cutoff are not publicly disclosed.2
Consequently, pretraining-data contamination cannot be completely excluded for either
backbone.
   Another internal threat concerns agent nondeterminism. The provider APIs do
not expose a controllable random seed, and each agent configuration is represented
by one archived run per issue. The reported effectiveness and efficiency differences
are therefore descriptive observations for the evaluated runs rather than estimates of
run-to-run variance. Repeated trials would be required to quantify the stability of file
rankings, interaction depth, token consumption, latency, and cost.
   External validity. The empirical evaluation is conducted exclusively on issue-fix
pairs collected from the Ollama repository. While Ollama supports a wide range of
programming languages, artifact types, and software subsystems, its architecture and
development trajectory focus on specific design goals that may differ from those of
other LLM inference engines, such as vLLM, llama.cpp, or TensorRT-LLM. Conse-
quently, these findings serve as a preliminary insight, and more extensive cross-project
evaluations are needed to confirm their broader applicability.

6.2. Future Research
Based on the limitations and findings of this thesis, we propose the following directions
for future research:

  1. Root-Cause-to-Fix-Strategy Knowledge for Fault Localization: Liu et al. [Liu+26b]
     map their root-cause taxonomy to common fix strategies observed in LLM infer-
     ence engine repositories. A predicted root cause may narrow the set of plausible
     fix strategies, while those strategies may in turn indicate the software layers,
     artifact types, or files most likely to require modification. It is therefore worth
     examining whether incorporating this root-cause-to-fix-strategy mapping as ex-
     ternal diagnostic knowledge can indirectly assist file-level fault localization and
     improve the candidate ranking produced by ClueFL.

  2. Cross-Engine and Cross-Backbone Evaluation: The current evaluation studies
     a single LLM inference engine, Ollama, with GPT-5.2 and DeepSeek V4 Pro as
     two representative backbone models. Future work should construct comparable
     issue–fix datasets for additional inference engines, such as vLLM, llama.cpp, and
     TensorRT-LLM, and evaluate ClueFL with a broader range of proprietary and
     open-weight backbones. This would test whether the observed improvements
     generalize across repository architectures and model configurations with different
     reasoning capabilities, tool-use behavior, context capacities, and computational
     costs.

  3. Repeated-Run Robustness and Efficiency Evaluation: The current study reports
     interaction steps, processed tokens, wall-clock duration, and available or estimated
     API cost, but each agent configuration contributes only one stochastic run per
     issue. Future work should repeat each matched configuration and report the
     variation in Top-k accuracy and MRR@5 together with distributions of token usage,
     tool calls, latency, and monetary cost. Such an evaluation would clarify both
     the stability of the rankings and the tail behavior of the effectiveness–efficiency
     trade-off.

  4. User Study of ClueFL: Although a practitioner survey suggests that inspecting at
     most five suspicious program elements constitutes an acceptable fault-localization
     success criterion for many developers [Koc+16], and a prior user study shows that
     fault-localization tools can significantly reduce professional developers’ debug-
     ging time [Xia+16], there is currently no direct evidence that ClueFL can reduce
     repair time or improve repair accuracy for developers maintaining the Ollama
     repository. Therefore, future user studies should invite Ollama maintainers or




                                           53
                               6. Discussion and Conclusion


     contributors to perform real-world software maintenance tasks and evaluate the
     practical impact of ClueFL on repair efficiency and correctness.


6.3. Summary
In this thesis, we evaluated various file-level fault localization approaches for LLM
inference engines by constructing a dataset of existing Ollama issue-fix pairs. We then
developed the ClueFL framework and demonstrated that domain-specific guidance
and a well-designed workflow, as implemented in ClueFL, improve an agent’s ability
to prioritize repair locations for Ollama issues. By moving beyond flat repository
exploration toward cross-software-layer understanding, this work provides a foundation
for diagnostic tools that support fault localization and maintenance in large-scale LLM
infrastructure.
